A language model on its own does one thing: given a prompt, it produces text. In a chat window that is the whole loop: **model → prompt → output**. You copy code in, copy the answer out, and you are the one who runs it, tests it and notices what is wrong.

An **agent** closes that loop. It wraps the model in a **harness**: the software around the model that lets it read files, run commands, look at the results and try again. GitHub Copilot's agent mode, Claude Code and Mistral Vibe are all harnesses.

## Same task, two ways

A small task, similar to the W3 demo: *add an About button to the home screen.* Step through both ways of doing it, and watch who carries the tool output.

<Predict id="race-handoffs" question="In the chat version, how many times will <b>you</b> have to copy something between the chat and your project before the task is done? And with the agent?">

Four with the chat: the file and the task into the chat, the answer into your file, the error back into the chat, the fix into your file. None with the agent. The model is the same in both columns. What changes is who sees the analyzer's output first.

| Part of the harness | What it does | Where you meet it in this course |
|---|---|---|
| **Tools** | Let the model act: read and edit files, run commands, search the code | Copilot's agent runs `flutter test` and reads the output itself |
| **Automation** | Runs the loop: plan, act, look at the result, repeat until done or stuck | The agent fixes an analyzer error without you pasting it back |
| **Instructions** | Frame each task: the prompt, plus **agent skills** (`.github/skills/<name>/SKILL.md`) that the agent loads only when the task needs them | The task prompts in W3 and W4; the course's `ba-*` and `mh-*` skills |
| **Standards** | Project rules the agent must follow on every task | `AGENTS.md` in the Mood Tracker and in your pair's repository |

Two consequences matter in practice:

1. **The same model in a different harness is a different agent.** A Claude, Gemini or GPT model behaves differently in Copilot, in a command-line agent and in a chat window, because it has different tools, loops and rules around it. In the lectures you first compare models inside Copilot: same harness, different model.
2. **When an agent does poor work, fix the harness first.** Missing rules, missing project knowledge, a vague task or a tool it cannot run are far more common causes than "the model is bad". A bigger model does not know a rule nobody wrote down.

:::note[MCP: plugging more tools into a harness]
The **Model Context Protocol (MCP)** is an open protocol for connecting extra tools and data sources to a harness: a design tool, a database, an issue tracker. In W5 you write your own MCP server and connect it to Copilot. In VS Code, a workspace `.mcp.json` file is the portable place to configure it; the older `.vscode/mcp.json` still works but is marked as deprecated.
:::

## Every tool is also a way in

An agent acts with **your** permissions. Everything it reads can contain instructions: an issue, a web page, a tool's output, a comment in a dependency. The model cannot reliably tell data from commands. Text that steers an agent this way is called **prompt injection**.

The danger is highest when one session has all three of these at once, which Simon Willison calls the **lethal trifecta**:

1. access to private data (your code, `.env`, participants' data);
2. exposure to untrusted content (issues, web pages, files from strangers);
3. a way to send data out (a web request, a push, a comment, an email).

Remove at least one of the three. In practice:

- Approve the agent's commands instead of letting it run everything automatically.
- Give MCP servers read-only tokens with the narrowest scope that works.
- Run tasks on untrusted content in a sandbox: a container, or the cloud agent's environment.
- Never let an agent that reads public issues also hold secrets it could send out.

W5 covers the attacks in detail (OWASP Top 10 for LLM applications and for agentic applications).

<AtWork>Teams now set up agents for the whole repository. Showing that you can tune a harness (instructions, tools, permissions) with a concrete example is something you can put on a CV.</AtWork>

:::tip[Do this in your project]
Ask your agent, in a fresh session: *"Which tools can you use here, which instruction files did you read, and which commands may you run without asking me?"* Compare the answer with your `AGENTS.md` and your tool's settings. Fix the first gap you find, and switch off automatic approval of commands if it is on.
:::
