`AGENTS.md` is a Markdown file in the root of a repository, written for coding agents rather than for people. Many agents read it automatically at the start of each task, so it is their **entry point** into the project. You wrote your pair's first version in W2.

Which tools read it (checked in November 2026):

- **GitHub Copilot** reads `AGENTS.md` in VS Code, in Copilot CLI and in the Copilot cloud agent (formerly "coding agent"). It also has its own files: `.github/copilot-instructions.md` for the whole repository and `.github/instructions/*.instructions.md` for parts of it.
- **Claude Code** reads its own `CLAUDE.md`. Recent versions fall back to `AGENTS.md` when there is no `CLAUDE.md`; the safe way that works in every version is a `CLAUDE.md` containing the line `@AGENTS.md`, which imports it.
- **Other agents**: more than twenty tools follow the [agents.md](https://agents.md/) format. Support still changes quickly, so check in practice: ask the agent which instruction files it read.

A useful `AGENTS.md` answers seven questions. The examples are from the Mood Tracker's own `AGENTS.md`:

| Section | Question it answers | Example line |
|---|---|---|
| **How we work** | What cycle does every change follow? | "Restate the task, plan before editing, make the smallest change, verify, report, stop and ask." |
| **Project knowledge** | Where are the documents about the system and the client? | "Product card: `docs/product.md`. What the client actually said: `docs/client-log.md`." |
| **Architecture** | What exists, and what may depend on what? | "Routers never import `app.config` directly." (checked by import-linter) |
| **Specifications** | What must exist before code? | "One test per acceptance criterion; put the criterion ID (`AC-1`) in the test name." |
| **Commit standards** | What must a commit say? | "Commit messages and AI attribution follow `docs/commits.md`." |
| **Boundaries** | What is out of bounds? | "Do not weaken, skip or delete tests to make them pass." |
| **Reporting** | How must the agent report? | "Label every claim: FACT (with `file:line`), HYPOTHESIS, UNKNOWN." |

<Predict id="agents-md-limits" question="In W2 you compared the agent's claims about the code without and with an <code>AGENTS.md</code>. Whatever the difference was, what can even a very good <code>AGENTS.md</code> <b>not</b> fix?">

It cannot replace checking, and it cannot contain knowledge nobody wrote down. An agent that follows every rule can still be wrong about a fact. That is why the reporting format separates FACT from HYPOTHESIS, and why claims get checked with a command, a test or a run.

</Predict>

## From a request to enforcement

A rule can live in three places, from weakest to strongest:

| Where | Example | What enforces it |
|---|---|---|
| **A sentence** in `AGENTS.md` | "Do not edit files in `test/` to make a test pass." | Nothing. The model usually follows it. |
| **A hook**: a script the harness runs before or after an agent's action | A script that blocks any edit under `test/` unless you approve it | The harness, every time, whatever the model decides |
| **A check** in the quality gate | A test that fails when a screen imports `http` | The gate, for every change by anyone (stage 6) |

Every line of `AGENTS.md` is read on every task, so it costs context every time. If a rule can be checked by a tool (a lint rule, a formatter, an architecture test, `import-linter`), put it in the tool and mention the command in `AGENTS.md`. The Mood Tracker's `AGENTS.md` says which rules are checked and which are only conventions: that line tells you where to add the next test.

Section 7 has a full template.

:::tip[Do this in your project]
Pick one rule in your `AGENTS.md` that is marked "convention, not checked", or that you have had to repeat to the agent. Turn it into a test or a lint rule, run it, and move the rule to "checked by `<test>`".
:::
