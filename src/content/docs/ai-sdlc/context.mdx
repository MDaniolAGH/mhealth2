The model knows nothing about your project except what is in its **context window** for the current task. Everything the agent works from has to fit there.

The context of a running agent holds:

- **Rules**: `AGENTS.md` and the task prompt.
- **Project knowledge**: the architecture, decision records, notes and product card it has read (section 3).
- **Code** the agent has opened.
- **Work log**: its own earlier steps and every tool output, such as a long test run.
- **Changes**: the diffs made so far.

Context windows in current models are large: hundreds of thousands of tokens, and up to about a million for some. Filling them is still a bad idea:

- **Cost.** Every step of the loop sends the context again, and you pay for it in time and money (in Copilot, in premium requests). Less context means lower cost.
- **Focus.** Irrelevant files and stale tool output compete with what matters. A long session slowly fills with old logs, and in W2 you saw a long session break a rule a fresh one followed.
- **Sub-agents** help. A large task can be split so that each part starts with a fresh, small context:

The opposite failure is **missing information**. A model does not stop when it lacks a fact; it fills the gap with something plausible. For the About screen, the most dangerous gap is the client's own words: an agent that has not read `docs/product.md` will write an intended purpose and a contact address, and both will look exactly like real ones.

That is why this pipeline does two things. It gives the agent the facts it needs: the goal, the criteria and, above all, the **project knowledge**. And it demands **evidence**: tests written against your criteria and gates that run without anyone's opinion. A test turns "looks right" into "checked".

:::tip[What to put in the context, and what to leave out]
- **Include**: the criteria, the files the change touches, the relevant project documents, the project rules.
- **Leave out**: the whole repository "just in case", old chat history, unrelated logs.
- **Never include** passwords, API keys, the server's `.env`, or real personal or health data. The context is sent to the model's provider.
- **Start a fresh session** when a task is finished, after writing down in `NOTES.md` what the next session needs to know.
:::
