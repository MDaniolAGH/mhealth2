## Given, When, Then

A story becomes testable when it has **acceptance criteria**: concrete situations with an observable result.

> **Given** *[the context]*, **when** *[an action or event]*, **then** *[an observable result]*.

Story S2 from the previous page, with its two riskiest criteria:

```text title="S2: acceptance criteria (excerpt)"
Given the server does not answer,
When the participant opens the About screen and waits 5 seconds,
Then the screen shows "Server: unavailable",
 and the purpose and the contact are still shown.

Given the client has not confirmed a contact yet,
When the participant opens the About screen,
Then the contact line shows "not yet confirmed".
```

These are AC-4 and AC-5 of the [AI SDLC example](../../ai-sdlc/idea-to-plan/#stage-requirements). The story's criteria *are* the specification the agent will plan from; the EARS form there says the same thing as one sentence. Agents are good at proposing edge cases (no network, no contact, very long text, a large font). You decide which ones matter to this client.

## A light INVEST check

| Letter | The story is… | Quick check |
|---|---|---|
| **I**ndependent | buildable without waiting for another story | Can it ship alone? |
| **N**egotiable | a need, not a contract for one solution | Does it name a package, a button, a vendor? |
| **V**aluable | worth something to a person | Who notices if it is missing? |
| **E**stimable | clear enough to estimate | Could you give a three-point estimate? |
| **S**mall | done and checked in a few days | Would you split it if you had to? |
| **T**estable | true or false by a test or a run | Is there at least one Given/When/Then? |

## Priorities: Must, Should, Could, Won't

**MoSCoW** priorities are the client's call; you propose and explain the trade-offs. *Won't (this time)* is a useful answer: it records that something was considered and left out on purpose.

| **Should** | the app version (S1) | support asked for it; the phone's settings are a workaround |
| **Could** | the server version | useful for support, not requested |
| **Won't** | a licences page; a changelog | out of scope for this study |

## Splitting stories

When a story is too big, split it so that **each part still delivers value** on its own. Agents propose splits well; check that each slice is something a person would notice.

- **By rule or edge case**: the server answers / does not answer.
- **By data**: the purpose text / the version numbers.
- **By user**: the participant / the support person.
- **Simple case first**: the screen with fixed text, then the server version.

Splitting by technical layer ("the service", "the screen", "the tests") is not a split: none of the slices is useful alone.

## One word, one meaning

Many arguments are not about data but about words. A term is defined when two people, given the same case, would classify it the same way. The client owns the meaning; you find the cases that need deciding.

| Term | Proposed definition | Edge cases and the rule | Owner |
|---|---|---|---|
| **App version** | the version and build number of the installed build, e.g. `1.3.0 (12)` | a debug build: show "dev"; an update during the study: show the new version, no history | coordinator: *to confirm* |
| **Server version** | the version the server reports at `GET /version` | the server is down: "unavailable"; an older server without `/version`: "unknown" | your pair |
| **Contact** | the person and channel the clinic named for participants' questions | not named yet: "not yet confirmed"; out of hours: *to decide by the client* | coordinator |

<Predict id="term-version" question="Support asks a participant: &quot;Which version do you have?&quot; The participant reads &quot;1.3.0 (12)&quot; from the About screen, while the phone's settings say &quot;1.3.0&quot;. Is that a problem?">

Only if nobody defined the term. With the definition above, support knows that the number in brackets is the build, and that two builds can share 1.3.0. Without it, support and your pair will mean different things by "version", and a bug report will point to the wrong build. Definitions are cheap before release and expensive after.

</Predict>
