## The decision before the solution

A client rarely needs "an app". They need to **make a decision**. Name it before you propose anything, or the agent will name a solution for you, and every later document will be about that solution.

	title="Monday, 11:00: asking Copilot for the decision"

		{ who: 'you', name: 'You', text: '@Copilot write the decision Anna has to make. Use only the brief and the client log.' },
		{ who: 'agent', name: 'Copilot', text: 'Decision: implement an About screen using <code>package_info_plus</code>, showing the app version and a support contact.' },
		{ who: 'you', name: 'You', text: 'That is a solution, with a package in it. Rewrite it as a decision: no technology names, and at least one option without software.' },
		{ who: 'agent', name: 'Copilot', text: 'Anna must decide how participants learn what the app is for and whom to contact, and how Tomek learns which version they run: in the app, on paper, or both.' },
		{ who: 'client', name: 'Anna', text: 'Yes. That is exactly what I need to decide. 👍' },
	]}

> *[Who] must decide whether to [option A], [option B] or [option C], so that [goal], within [key constraints].*

For the clinic:

```text title="docs/decision.md (illustrative)"
Decision  The study coordinator must decide how participants learn what the
          app is for and whom to contact, and how support learns which version
          a participant runs: in the app, in the consent documents, or both,
          so that the ethics committee's request is met,
          before the next participant group starts, without new cloud services.
Options   keep as is | consent form + printed sheet | a screen in the app |
          the study web page
Sources   client log 2026-11-12 (coordinator; ethics committee request)
```

No technology names, and at least one option that is not software. "Build an About screen" is a solution; it appears later, as one of the options.

## Facts, assumptions and unknowns

Every recommendation rests on assumptions. Make them visible, so they can be checked before they become expensive.

- **Fact**: stated in the brief or by the client, or shown in the code or the app, **with a source**.
- **Assumption**: something you treat as true without confirmation. Useful only if it is specific enough to be wrong.
- **Unknown**: something you know you do not know. It becomes a question.

Rank assumptions by the **damage if they are wrong**, not by how likely they feel. And record where each came from: *validated*, *client said (date)*, *agent-generated* or *unknown*. An agent-generated statement is never a fact, however confident it sounds.

:::caution[Synthetic users are not users]
An agent can role-play a patient, a nurse or a coordinator in seconds. These **synthetic users** produce no new information: they reflect the model's training data and your prompt, and they tend to agree with you. Use them to prepare an interview guide or to find questions you forgot. Never use them as evidence, and never write what they "said" into the client log.
:::

## Stakeholders and data flows

Requirements come from people, and conflicts between people are often the real requirements. Include those who are affected but not paying.

| Stakeholder | Goal | Concern | Influence |
|---|---|---|---|
| Study coordinator (client) | ethics approval; fewer support calls | wrong or unapproved text in the app | decides |
| Ethics committee | participants know what the app is for | a purpose that claims too much | can block the study |
| Participants | know what the app is for and whom to ask | confusion; being asked for more data | use it, or stop using it |
| Support person at the clinic | know which version a participant runs | time spent on calls without context | none formally; high in practice |
| Your pair (maintainers) | a change you can build, test and explain | text that changes every week | proposes |

| Data | From | To | Purpose | Agreed? |
|---|---|---|---|---|
| App version | the build | the screen, then support (read out by the participant) | find out whether a reported problem is already fixed | yes |
| Server version | `GET /version` | the screen | the same, for the server | to confirm |
| Purpose sentence, contact | the client log, via `docs/product.md` | the screen | participants know the purpose and whom to ask | contact: **not yet** |

The About screen shows no data about the participant. Keep it that way: adding the participant's ID "to help support" would be a new flow of personal data that nobody has agreed to.
