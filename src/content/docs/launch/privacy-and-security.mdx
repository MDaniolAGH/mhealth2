## Health data and the GDPR

Self-reported mood is **health data** ("data concerning health"), one of the special categories of personal data under Article 9 of the GDPR, whether or not the app is a medical device. Two roles matter:

- The **controller** (the clinic) decides why and how personal data is processed: the legal basis, whether a data protection impact assessment (**DPIA**, Article 35) is needed, how long data is kept.
- **You** build what makes compliance possible, or impossible. You do not decide the legal basis; you make sure the system can do what the controller promises.

Start with a **data inventory**: every data item, where it lives, who can see it, how long it is kept, and **why** it exists. Data lives in more places than the database: the phone's storage, caches, logs, backups, crash reports, test fixtures, and anything you paste into an AI tool.

The rights of the participants have to work **technically**: access, rectification, erasure, restriction, portability. For each one, ask: can the system do it, and how long does it take? Write what only the controller can decide as **questions**, not answers. And never claim that a system "is GDPR compliant": compliance is not a property of code alone. In Poland, the supervisory authority for data protection is UODO (*Urząd Ochrony Danych Osobowych*).

:::caution[AI tools are processors too]
Pasting participants' data into an AI tool sends it to another company. In this course, use synthetic data only. In a real project, any service that processes personal data on the controller's behalf (hosting, crash reporting, an AI API) needs a contract and a place in the data inventory.
:::

## Risk: harm first, then code

Risk management for medical devices, including software (ISO 14971), asks first **what could go wrong for a person**, and only then what could go wrong in the code. It is good practice for any health app.

- **Hazard**: a source of harm (wrong information shown).
- **Sequence of events → hazardous situation**: how a person gets exposed.
- **Harm**: injury or damage to health, or, more broadly, to privacy.
- **Risk control**, in this order: a safer design first, then protective measures, then information. Every control needs a way to **verify** it.

```text title="Risk table (excerpt, About screen, illustrative)"
# | Hazard                 | Sequence → hazardous situation                 | Harm
1 | Wrong contact shown    | contact was guessed or outdated → a participant | delayed help in a
  |                        | in distress calls a number nobody answers       | crisis (serious)
2 | Purpose claims too     | store text says "helps manage depression" →     | wrong reliance on
  | much                   | a participant uses the app instead of care      | the app (serious)

Controls
1 | Contact only from the client log; "not yet confirmed" until then (AC-5);
  | the line "In an emergency, call 112" on the screen        → verified by AC-5 test, review
2 | Store text copied from the purpose; review checklist item → verified by release checklist
```

<Predict id="worst" question="Of all the About screen's fields, which one could cause the most serious harm if it were wrong: the app version, the server version, the purpose, or the contact?">

The **contact**. A wrong version annoys support. A wrong contact can leave a person in distress without help. That is why AC-5 forbids invented contacts, and why the risk table adds an emergency line. Risk analysis often moves your attention from the most complex code to the simplest text.

## Mobile and API security

Two OWASP checklists cover most of it: **MASVS** for the app and the **API Security Top 10** for the server. Course skills: `/mh-owasp-masvs`, `/mh-owasp-api`, `/mh-secrets-and-config`.

| MASVS group | The question for a health app |
|---|---|
| STORAGE | Where does the app keep health data and tokens? Encrypted? Copied into cloud backups? |
| CRYPTO | Platform crypto and sound key handling, not home-made? |
| AUTH | What happens on logout and when a token expires? |
| NETWORK | TLS everywhere? Any cleartext left from debugging? |
| PLATFORM | Deep links, WebViews, screenshots of sensitive screens? |
| CODE | Dependencies current? Input validated? |
| RESILIENCE | Does the threat model justify anti-tampering? Often not for a pilot; say why |
| PRIVACY | Data collection minimal, transparent, under the user's control? |

:::danger[A mobile app cannot keep a secret]
Anything inside the app (constants, `--dart-define` values, assets) can be extracted by anyone who has the app. API keys for paid services, the server's JWT secret, database passwords: never in the app. A development default that "only works locally" is a finding if nothing stops it from reaching production.
:::

For the API, check the way an attacker would, with requests and two synthetic users. The first question is almost always: **can user A read or change user B's data by changing an ID?** (API1, broken object-level authorisation).

## The evidence pack

Everything from Part 2 becomes evidence here: goals, acceptance criteria, tests, pull requests, decision records. For medical software, IEC 62304 asks for this **traceability**: requirement → design → code → test, and for every risk control a test. It also asks for a **SOUP** list: every third-party library, with its version, why it is there, and its known problems. The software's **safety class** (A, B or C) depends on the worst harm a software failure could contribute to, and decides how much process is required.

Even for a diary, the same pack answers the questions a client, an auditor or the next team will ask.
