This page follows the story of Andrej Karpathy's lecture [*Deep Dive into LLMs like ChatGPT*](https://www.youtube.com/watch?v=7xTGNNLPyMI) (2025), which is worth watching in full. It is here because every rule in Parts 1–3, from "give the agent the client log" to "never trust a number without a source", comes from how these models work.

## 1. It starts with the internet

A model is first trained on a huge amount of text. Builders download web pages and filter them: drop unwanted sites, extract the text, keep the languages they want, remove duplicates, remove personal information. What is left is the **pre-training data**. One open example, Hugging Face's FineWeb, holds about **15 trillion tokens** (about 44 TB of text).

The model will absorb the patterns of this text, including its facts, its style and its mistakes.

## 2. Tokens: what the model actually reads

A model does not read letters or words. Text is cut into **tokens**: frequent pieces of text, from single characters to whole words. The vocabulary is built from the data with an algorithm called byte-pair encoding: start from bytes, and keep merging the pairs that appear most often. GPT-2's tokenizer (2019) had about 50,000 tokens, GPT-4's about 100,000, GPT-4o's about 200,000.

Compare the rows. A bigger vocabulary, trained on more languages, cuts the same text into fewer, longer pieces: the Polish sentence goes from 19 tokens in GPT-2 to 13 in GPT-4o, the Russian one from 41 to 10, the Chinese word from 11 to 3. English barely changes: it was already cheap. The reference rows show the extremes: a model reading UTF-8 bytes would need a token for every byte, which is why Polish letters with diacritics (two bytes each) were so expensive for GPT-2.

The dots (·) stand for spaces: a space is usually part of the next token. Notice what the model can and cannot "see": it sees `straw` and `berry`, not ten letters. Keep that in mind for section 6.

## 3. The model predicts the next token

The neural network is a mathematical function with billions of **parameters** (weights). It takes a window of tokens and outputs a **probability for every token in the vocabulary**: how likely each one is to come next.

**Training** shows it trillions of real examples and nudges the parameters so that the token that really came next gets a slightly higher probability. **Using** the model (inference) means: pick a next token from the probabilities, add it to the window, and repeat. Every answer you have ever read from a chatbot was written this way, one token at a time.

The pick is random, weighted by the probabilities. **Temperature** controls how random: low temperature sharpens the distribution towards the top token, high temperature flattens it.

This is why the same prompt gives different answers: the effect behind the W2 exercise “Seven answers”, where every pair sent Copilot the same prompt. In tools like Copilot you cannot set the temperature yourself, so you get variation whether you want it or not.

## 4. From internet simulator to assistant

A model trained only on web text is a **base model**: Karpathy calls it an internet document simulator. Give it the start of a page, and it continues the page. It does not answer questions; it writes what usually comes next.

## 5. Two kinds of memory

<Predict id="memory" question="You ask a model about a detail of the Mood Tracker's code. When is it more likely to be right: when it relies on what it learned in training, or when the file is in its context?">

When the file is in the **context**. Karpathy's distinction: knowledge in the parameters is like a **vague recollection** of something you read months ago; the context window is **working memory**, sharp and directly available. That is the whole idea behind Part 2: put the client log, the architecture and the right files in the context, instead of relying on what the model half-remembers.

</Predict>

| | Parameters (weights) | Context window |
|---|---|---|
| Like | a vague memory of what you once read | what is on the desk in front of you |
| Contains | patterns from the training data | your prompt, the files, tool output |
| Up to date? | frozen at the end of training | as current as what you put in |
| Your control | none | complete: that is context engineering |

## 6. Hallucinations and the Swiss cheese

Models **hallucinate**: they produce fluent, confident text that is false. In training, confident answers were almost always the right style, so a model imitates confidence even when it does not know. Labs reduce this by training models to say "I don't know" and by giving them **tools** (search, running code), but it never goes away.

Capabilities are also uneven. Karpathy compares them to **Swiss cheese**: brilliant at hard problems, with random holes in easy ones.

- **Counting letters.** The model sees `straw` + `berry`, not letters, so "how many r's in strawberry?" can go wrong. Ask it to write code that counts, and it gets it right.
- **9.11 or 9.9?** Some models have said 9.11 is bigger, possibly because in many texts, such as Bible verses or version numbers, 9.11 comes after 9.9.
- **Models need tokens to think.** Each token gets a fixed amount of computation. An answer squeezed into one token has had little "thinking"; working step by step, in many tokens, or with a tool, is more reliable.

## What this means for you

- **Tokens** are the unit of cost and of the context window. Polish text costs more of both.
- **Sampling** means variation: check results, not wording. Run important prompts more than once.
- **Working memory beats vague memory:** give the model the facts (Part 2, context and project knowledge).
- **Plausible is not true:** facts need sources (Part 1), numbers need tools, and claims about code need `file:line`.
