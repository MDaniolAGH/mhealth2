## 5. Implementacja

<StageFacts tone="agent" who={'<span class="sdlc-chip is-agent">Agent</span> w swoim harnessie'} input="Zatwierdzony plan, <code>NOTES.md</code>, <code>AGENTS.md</code>" output="Małe zmiany na branchu, łatwe do przejrzenia, każda z wiadomością commita wyjaśniającą, dlaczego powstała" />

Agent pracuje na **branchu** (tutaj `feat/about-screen`), nigdy bezpośrednio na `main`. Realizuje plan i trzyma się ustalonych w nim standardów, architektury i interfejsów. Po każdej zmianie uruchamia sprawdzenia (etap 6) i poprawia kod w pętli, dopóki nie przejdą. Na W4 uruchamialiście kilka agentów równolegle, każdego w osobnym **worktree** (drugi folder roboczy tego samego repozytorium, na własnym branchu), żeby dwóch agentów nigdy nie edytowało tych samych plików.

Całe issue możesz też przypisać do **Copilot cloud agent**, który pracuje w sandboxie na GitHubie i otwiera pull request. Pipeline się przez to nie zmienia. Issue musi zawierać kryteria, pull request przechodzi przez ten sam gate, a ty robisz review tak samo jak w przypadku pull requesta od kogoś z zespołu.

Każda zmiana kończy się **commitem**, a wiadomość commita też jest częścią dokumentacji. Dobra wiadomość mówi nie tylko, *co* się zmieniło, lecz także *dlaczego*, jak to *zweryfikowano* i jak *powstało*. Oto format przyjęty na kursie (`docs/commits.md`):

```text title="Wiadomość commita (przykład)"
feat(app): add About screen with app and server version

Participants and support could not tell which version was installed, and
the agreed intended purpose was not visible in the app.

Verified: flutter analyze → <paste the real result>
Verified: flutter test → <paste the real summary line>
Not verified: iOS simulator
Refs: GOAL-1
ADR: ADR-0003
AI-assisted: GitHub Copilot (agent) / <model>
Decision: <accepted|revised>
Time: <minutes> min
Cost: <AI credits|unknown>
```

Linie `Key: value` na końcu to **trailery Gita**. Git i inne narzędzia potrafią je odczytać, więc `git log --grep="GOAL-1"` wypisze każdy commit związany z tym celem, a linie dotyczące AI trafiają do logu agenta twojej pary. Agent nigdy nie wypełnia pól *Decision*, *Time* ani *Cost*: to twoja działka.

:::note[Commit robisz ty]
`AGENTS.md` Mood Trackera mówi: *do not commit, push or open pull requests unless asked.* Najpierw robisz review diffu, potem commitujesz z wiadomością taką jak powyżej. Odrzucone próby nie trafiają do commitów, tylko do `dossier/rejected.csv`.
:::

:::caution[Co tu najczęściej idzie nie tak]
- Jeden gigantyczny commit o nazwie „add about”.
- Zmiany w plikach, o których plan nie wspominał.
- „Naprawianie” padającego testu przez osłabienie go albo ponowne wygenerowanie pliku golden, żeby test przeszedł. `AGENTS.md` zabrania jednego i drugiego, a diff to ujawnia.
:::

## 6. Quality gate: co musi być spełnione, zanim ktokolwiek przeczyta kod

<StageFacts tone="tool" who={'<span class="sdlc-chip is-tool">Narzędzia deterministyczne</span>'} input="Zmieniony kod" output="Zaliczone albo dokładny komunikat błędu, który wraca do agenta" />

**Quality gate** to zestaw automatycznych sprawdzeń, przez które musi przejść każda zmiana, zanim pójdzie dalej. Nie zaczynaj od listy narzędzi. Zacznij od pytań: **czego musimy być pewni przy każdej zmianie, za każdym razem, niezależnie od tego, kto albo co ją napisał?** Każde narzędzie to tylko jeden ze sposobów odpowiedzi na któreś z tych pytań.

### Czego chcemy być pewni

| # | Pytanie | Dlaczego to ważne | Rodzaj sprawdzenia | Jak to zrobić w Mood Trackerze |
|---|---|---|---|---|
| 1 | **Czy kod jest poprawnie zbudowany?** | Kod, który się nie kompiluje albo ma błędy typów, od tej chwili marnuje wszystkim czas | analiza statyczna | `flutter analyze` |
| 2 | **Czy jest napisany tak, jak u nas się pisze?** | Spójny kod czyta się szybciej, a styl przestaje być tematem review | reguły lintera, formatowanie | `flutter_lints`, `dart format` |
| 3 | **Czy szanuje architekturę?** | Warstwy rozmywają się przez kolejne „małe wyjątki”, a agenci kopiują każdy wzorzec, jaki zobaczą | reguły zależności | `lint-imports` (serwer); test dla aplikacji (poniżej) |
| 4 | **Czy można to bezpiecznie udostępnić?** | Klucz albo hasło w historii Gita jest publiczne w chwili, w której publiczne staje się repozytorium | secret scan | git-secrets, gitleaks |
| 5 | **Czy możemy ufać temu, od czego zależy?** | Każdy pakiet to cudzy kod, którego nikt z was nie przejrzał: pozycja SOUP, którą trzeba zarejestrować i monitorować | skan podatności, sprawdzenie rejestru | OSV-Scanner; `tests/test_soup_register.py` |
| 6 | **Czy UI nadal wygląda tak, jak zatwierdzono?** | Drobne zmiany wizualne prześlizgują się przez code review | porównanie zrzutów ekranu | golden testy (`matchesGoldenFile`) |

W gate celowo **nie ma** dwóch pytań. Na pytanie *czy kod robi to, o co prosiliśmy?* odpowiadają testy względem kryteriów (etap 7), a na pytanie *czy w ogóle warto to budować?* – tylko ludzie (etapy 7 i 10).

### Kiedy sprawdzenie staje się gate'em

- **Deterministyczne.** Dla tego samego wejścia werdykt jest zawsze ten sam. Model językowy nie daje takiej gwarancji – i właśnie dlatego gate istnieje.
- **Wiążące i z dowodami.** Zaliczone albo nie, nigdy „prawie”. Gdy sprawdzenie zostanie oznaczone jako **required** w regułach ochrony branchy w repozytorium, porażka blokuje merge i nikt, ani człowiek, ani agent, nie może z nią dyskutować. Każde uruchomienie zostawia log: które narzędzie, w jakiej wersji, co powiedziało o którym commicie.
- **Fail-closed.** Jeśli sprawdzenia nie da się uruchomić (brakuje narzędzia, wysypało się), liczy się to jako porażka, a nie zaliczenie.
- **Zapadka.** Reguły mogą się tylko zaostrzać. Nigdy nie osłabiaj reguły, nie edytuj `.importlinter` ani nie usuwaj testu, żeby zmiana przeszła. Zabrania tego `AGENTS.md`, a diff i tak to pokaże.

Gate jest też **niezależny od autora**: opinia agenta o własnym kodzie nie jest dowodem, a werdykt gate'u – tak.

### Warstwy obrony

Żadne pojedyncze sprawdzenie nie łapie wszystkiego. Traktuj gate jak zestaw warstw – plastrów w modelu „sera szwajcarskiego” znanym z nauk o bezpieczeństwie. Każda warstwa zadaje **jedno pytanie** i przepuszcza każdy defekt, którego to pytanie nie obejmuje. Defekt dociera do użytkownika tylko wtedy, gdy przejdzie przez wszystkie warstwy.

**Wybierz defekt** i śledź go w dół: każda warstwa pokazuje, czy go przepuszcza, czy zatrzymuje.

<GateLab />

Gate jest tani i daje pewność w kilku sprawach. Testy sprawdzają to, o co prosisz. Ludzie – czy w ogóle warto było o to prosić. Potrzebujesz wszystkich trzech.

### Czego gate ci nie powie

:::danger[Zaliczony gate nie oznacza poprawnej funkcji]
Mood Tracker, który przejmujesz, przechodzi `flutter analyze` i wszystkie swoje testy. Wiesz więc, że kod jest poprawnie zbudowany i robi to, co sprawdzają jego testy. Nie wiesz natomiast, czy robi to, czego potrzebuje klient – to masz sprawdzić na laboratoriach. Gate dowodzi, że kod jest poprawnie zbudowany, spójny i bezpieczny do udostępnienia. Dopiero testy względem twoich kryteriów i uruchomienie aplikacji pokazują, że robi to, o co prosisz.
:::

### Gdzie działa gate: jak najwcześniej

Im wcześniej działa sprawdzenie, tym tańsza poprawka. Te same sprawdzenia uruchamia się w trzech miejscach:

| Gdzie | Kiedy | Kto widzi porażkę | Koszt porażki |
|---|---|---|---|
| **Pętla agenta** | po każdej edycji (tak każe `AGENTS.md`) | agent, który ją poprawia | sekundy |
| **Pre-commit hook** | przed każdym commitem | ty, zanim zmiana trafi do historii | minuta |
| **CI na pull requeście** | przed merge'em; nie da się go pominąć, gdy jest required | wszyscy; merge jest zablokowany | cała runda: poprawka, push, czekanie |

<TabItem label="W CI">

```yaml title=".github/workflows/quality-gate.yml (minimalny przykład)"
name: quality-gate
on: pull_request
jobs:
  app:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: mood_tracker
    steps:
      - uses: actions/checkout@v7
      - uses: subosito/flutter-action@v2
        with:
          channel: stable
          flutter-version: 3.35.x   # the handover's pinned version
      - run: flutter pub get
      - run: dart format --output=none --set-exit-if-changed .
      - run: flutter analyze
      - run: flutter test
  api:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: mood-tracker-api
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v7
        with:
          python-version: '3.12'
      - run: pip install -r requirements.txt -r requirements-dev.txt
      - run: lint-imports
      - run: python -m pytest -q
```

Pliki golden nagrane na macOS mogą się na Linuksie różnić o kilka pikseli (zob. `NOTES.md`). Świadomie zdecyduj, gdzie uruchamiasz golden testy. Nigdy nie generuj ich od nowa tylko po to, żeby CI przeszło. W ustawieniach repozytorium oznacz oba joby jako **required** checks – w przeciwnym razie porażka skończy się tylko czerwonym krzyżykiem.

<TabItem label="Reguła architektury">

```dart title="test/architecture_test.dart"
import 'dart:io';

import 'package:flutter_test/flutter_test.dart';

// AGENTS.md: screens and widgets never import http, sqflite or secure storage.
const forbidden = [
  'package:http/',
  'package:sqflite/',
  'package:flutter_secure_storage/',
];

void main() {
  test('screens and widgets never import http, sqflite or secure storage', () {
    final offenders = [
      for (final dir in ['lib/screens', 'lib/widgets'])
        ...Directory(dir)
            .listSync(recursive: true)
            .whereType<File>()
            .where((file) => file.path.endsWith('.dart'))
            .where((file) => forbidden.any(file.readAsStringSync().contains))
            .map((file) => file.path),
    ];

    expect(offenders, isEmpty);
  });
}
```

`AGENTS.md` z przekazanego projektu wymienia tę regułę jako „not checked by a test yet”. Dzięki temu plikowi już jest sprawdzana. Sprawdziliśmy to na przekazanej wersji R0 (Flutter 3.35): test przechodzi, ale pada z `Actual: ['lib/screens/home_screen.dart']`, gdy tylko ten plik zaimportuje `package:http`.
