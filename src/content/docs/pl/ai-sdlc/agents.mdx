Sam model językowy robi jedną rzecz: dostaje prompt i generuje tekst. W oknie czatu to cała pętla: **model → prompt → wynik**. Wklejasz kod, kopiujesz odpowiedź i to ty ją uruchamiasz, testujesz i zauważasz, co jest nie tak.

**Agent** zamyka tę pętlę. Opakowuje model w **harness**: oprogramowanie wokół modelu, dzięki któremu model może czytać pliki, uruchamiać polecenia, oglądać wyniki i próbować jeszcze raz. Agent mode w GitHub Copilocie, Claude Code i Mistral Vibe to harnessy.

<HarnessLab />

## To samo zadanie na dwa sposoby

Małe zadanie, podobne do demo z W3: *dodaj przycisk About na ekranie głównym.* Przejdź krok po kroku przez oba sposoby i zwróć uwagę, kto przenosi wyniki narzędzi.

<Predict id="race-handoffs" question="Ile razy w wersji z czatem <b>ty</b> będziesz musieć coś skopiować między czatem a projektem, zanim zadanie będzie gotowe? A ile razy z agentem?">

Cztery razy z czatem: plik i zadanie do czatu, odpowiedź do pliku, błąd z powrotem do czatu, poprawka do pliku. Z agentem ani razu. Model w obu kolumnach jest ten sam. Zmienia się to, kto pierwszy widzi wynik analyzera.

</Predict>

<Race />

| Część harnessu | Co robi | Gdzie spotkasz ją na kursie |
|---|---|---|
| **Tools** | Pozwalają modelowi działać: czytać i edytować pliki, uruchamiać polecenia, przeszukiwać kod | Agent Copilota sam uruchamia `flutter test` i czyta wynik |
| **Automatyzacja** | Prowadzi pętlę: zaplanuj, zadziałaj, sprawdź wynik, powtarzaj, aż będzie gotowe albo agent utknie | Agent poprawia błąd z analyzera, a ty nie musisz go wklejać z powrotem |
| **Instrukcje** | Ustawiają ramy każdego zadania: prompt plus **agent skills** (`.github/skills/<name>/SKILL.md`), które agent wczytuje tylko wtedy, gdy zadanie tego wymaga | Prompty z zadaniami na W3 i W4; kursowe skille `ba-*` i `mh-*` |
| **Standardy** | Zasady projektu, których agent musi przestrzegać w każdym zadaniu | `AGENTS.md` w Mood Trackerze i w repozytorium twojej pary |

W praktyce liczą się dwie konsekwencje:

1. **Ten sam model w innym harnessie to inny agent.** Model Claude, Gemini czy GPT zachowuje się inaczej w Copilocie, w agencie w terminalu i w oknie czatu, bo ma wokół siebie inne tools, pętle i zasady. Na wykładach najpierw porównujesz modele w Copilocie: ten sam harness, inny model.
2. **Kiedy agent pracuje słabo, najpierw napraw harness.** Brakujące zasady, brakująca wiedza o projekcie, niejasno opisane zadanie albo tool, którego agent nie może uruchomić – to dużo częstsze przyczyny niż „model jest słaby”. Większy model nie zna zasady, której nikt nie zapisał.

:::note[MCP: podłączanie kolejnych tools do harnessu]
**Model Context Protocol (MCP)** to otwarty protokół do podłączania do harnessu dodatkowych tools i źródeł danych: narzędzia do projektowania, bazy danych, issue trackera. Na W5 piszesz własny serwer MCP i podłączasz go do Copilota. W VS Code przenośnym miejscem na konfigurację jest plik `.mcp.json` w workspace; starszy `.vscode/mcp.json` nadal działa, ale jest oznaczony jako przestarzały.
:::

## Każde narzędzie to też furtka

Agent działa z **twoimi** uprawnieniami. Wszystko, co czyta, może zawierać instrukcje: issue, strona internetowa, wynik narzędzia, komentarz w kodzie zależności. Model nie potrafi niezawodnie odróżnić danych od poleceń. Tekst, który w ten sposób steruje agentem, nazywa się **prompt injection**.

Największe ryzyko pojawia się wtedy, gdy jedna sesja ma naraz wszystkie trzy poniższe cechy. Simon Willison nazywa to **lethal trifecta**:

1. dostęp do prywatnych danych (twój kod, `.env`, dane uczestników);
2. kontakt z niezaufanymi treściami (issues, strony internetowe, pliki od obcych);
3. sposób, żeby wysłać dane na zewnątrz (zapytanie HTTP, push, komentarz, mail).

Usuń przynajmniej jedną z nich. W praktyce:

- Zatwierdzaj polecenia agenta, zamiast pozwalać mu uruchamiać wszystko automatycznie.
- Dawaj serwerom MCP tokeny tylko do odczytu, z możliwie najwęższym zakresem.
- Zadania, w których agent styka się z niezaufanymi treściami, uruchamiaj w sandboksie: w kontenerze albo w środowisku agenta w chmurze.
- Nigdy nie pozwól, żeby agent, który czyta publiczne issues, miał też dostęp do sekretów, które mógłby wysłać na zewnątrz.

Ataki omawiamy dokładnie na W5 (OWASP Top 10 dla aplikacji LLM i dla aplikacji agentowych).

:::tip[Zrób to w swoim projekcie]
Zapytaj agenta w nowej sesji: *„Z jakich tools możesz tu korzystać, które pliki z instrukcjami przeczytałeś i jakie polecenia możesz uruchamiać bez pytania mnie?”* Porównaj odpowiedź ze swoim `AGENTS.md` i z ustawieniami swojego narzędzia. Napraw pierwszą lukę, jaką znajdziesz, i wyłącz automatyczne zatwierdzanie poleceń, jeśli jest włączone.
:::
